# Proposal

## Why

分类回答"钱花在什么上",但回答不了"这笔钱在我的财务结构里算什么"——是每月必付的承诺、攒着做一件事、还是突然不得不花。这两个问题正交:同一笔"外卖"可以是日常,也可以是一次专项聚餐,靠分类分不出来。需要一个与分类、来源同级的维度来承载它。

这个维度按金额才显出价值——大额和一次性支出几乎都无法由分类推断,所以它必须是每笔交易的必填事实,不能靠默认值填。

## What Changes

- 新增"预算"维度:每笔交易(收入与支出皆然)有且只有一个预算,四个种子值 `固定` / `专项` / `突发` / `日常`,名字不含"支出"——收入同样挂预算(如利息收入归 `日常`)。
- 预算是可管理的表数据,不是写死的枚举:可查看、创建、改名、删除;被交易引用的预算不可删除。
- **BREAKING**:`create_transaction` 与 `update_transaction` 新增必填字段 `budget_id`。省略即拒绝,不记录、不修改。这与 `merchant`/`comment` 不同——后两者省略会被静默存为空字符串,`budget_id` 不允许。
- 交易查询与财务汇总纳入预算:可按预算筛选,汇总结果按预算拆分。
- 新增批量更新交易工具,一次调用改同一账本内多笔交易的引用字段(分类、来源、预算)。这是回填存量交易的前提,也顺带补上"合并分类只能逐笔更新"的缺口。
- 存量交易在升级时先落到一个临时的"未分配"状态,必须回填为真实预算后系统才算迁移完成;未分配状态在汇总里可见,不隐藏。
- 实践层(plugin skill)补充如何为交易选择预算的约定。选择规则是说明文字,不是服务端逻辑——服务端不包含任何"哪个分类该配哪个预算"的知识。

## Capabilities

### New Capabilities

- `budget-management`: 预算主数据的查看、创建、更新、删除,以及新建账本时的种子预算。
- `batch-transaction-update`: 一次调用更新同一账本内多笔交易的引用字段,走 preview → apply 两步确认。

### Modified Capabilities

- `transaction-recording`: 记录、更新、查询、搜索交易时纳入必填的 `budget_id`;读取历史未回填交易时返回其未分配状态。
- `financial-analytics`: 财务汇总按预算拆分,并支持按预算筛选。
- `ledger-management`: 新建账本时同时建立该账本的种子预算。
- `plugin-record-skill`: 记录交易时如何选择预算的约定。
- `plugin-query-skill`: 查询结果展示预算。
- `plugin-analysis-skill`: 按预算解读汇总结果的约定。
- `plugin-export-skill`: 导出时预算不进入导出文件的说明。
- `plugin-optimize-skill`: 合并分类改用批量更新,不再逐笔调用。

## Impact

- 事实层(`mcp/`):新增 `budgets` 表与 `transactions.budget_id` 列,需对已有数据库做一次性加列;新增预算管理与批量更新两类工具;交易的记录、更新、查询与财务汇总工具的入参和返回值都有变化。
- 实践层(`plugin/`):`record`、`query`、`analysis`、`export`、`optimize` 五个 skill 都要补充约定。
- 数据:已有交易在升级后处于未分配状态,需要一次回填才能恢复"每笔交易都有预算"这个不变量。
- 破坏性:任何调用 `create_transaction` / `update_transaction` 的现有客户端,升级后必须传 `budget_id`,否则被拒绝。

## Non-goals

- 预算额度、每月上限、超支提醒:那是"这类钱能花多少",与本 change 的"这笔钱算哪一类"是两个概念,不在这里做。
- 导出文件携带预算:目标导入格式只有固定的七列,塞不进去;导出不改动账本内的预算。
- 交易时间线面板按预算筛选:面板是独立的前端资源,另开 change,不阻塞本 change。
- 分类与预算的交叉汇总:需要时再加,本 change 只做按预算拆分。
