记一笔交易不是"调一次 create_transaction"这么简单。tally 把"账本数据的投影"(商户
惯用哪个分类、哪个来源)和"用户本人的偏好"(习惯层)分得很清楚——这个 skill 就是
在记录前后把这条边界落到具体动作上。

## 记录一笔新交易:标准流程

**1. 先例检索。** 记录前先用 `search_transactions(ledger_id, keyword=<商户名/关键词>)`
搜这个账本里 `comment` 命中同一商户或同一关键词的历史交易。命中的交易里,别人(也就是
用户自己)之前用的 `source_id`/`category_id` 就是先例——把它当默认值去用,不要凭空猜,
也不要每次都追问用户"这个算什么分类"。没搜到先例才需要问。

`keyword` 是大小写不敏感的子串匹配,**不支持通配符**——`%` 和 `_` 会被当成字面字符去
匹配,不是 SQL 里的模糊匹配符。不要为了"搜宽泛一点"往关键词里加这些符号,加了反而
可能因为原文里没有这个字面字符而搜不到。

**没搜到先例、且现有分类也没有合适的,才提议新建。** 没搜到先例时,先用
`list_categories(ledger_id)` 看看账本里有没有语义匹配的已有分类——只有连这个都没有,
才需要新建。新建不要跳过预览直接建:把"准备新建一个叫 XX 的分类(挂在 YY 下面)"
作为预览的一部分,和金额/来源等字段一起交给用户确认(见下一步)。用户确认后调用
`manage_category`(`operation="create"`)建好,拿到新分类的 `id` 后再据此记录;这是
非破坏性操作,不需要两步确认。如果用户不同意新建,追问该用哪个已有分类,不要自作
主张建。

**2. 对话预览,不直接写。** 检索完先例后,不要马上调 `create_transaction`。先在对话里
给用户一个结构化预览:金额、币种、来源、分类(如果分类是新建的,连同新建提议一起
展示)、发生时间、准备写入的 `comment` 原文。等用户确认或改完再写入。

这一步是纯对话层的软确认,和服务端的 `confirmation_token` 两步确认无关——那套机制只
用于破坏性/批量操作;`create_transaction` 本身是单步直写的工具,服务端不会替你二次拦。
预览是 skill 教的纪律,不是协议要求。

**3. comment 纪律。** 写入 `comment` 的必须是用户原始表达的凭据文本(账单原文、商户
原名、用户口头说的那句话),不是你归类判断后的解释。比如用户说"星巴克 32 块",
`comment` 就写这句原话或账单上的商户原名,不要写成"餐饮消费"这种你脑补的归类结果。

这样以后 `search_transactions(keyword=...)` 才能真正搜到先例——`comment` 里留的是
"原文",结构化字段留的是"解释",两层信息都在,缺一层这套先例检索就废了。

**tally 没有独立的商户字段,`comment` 是唯一能被 `search_transactions` 命中的地方。**
所以 `comment` 要同时带上商户原名**和**足以区分这一笔的商品/事由明细,不能只留其中
一个。"星巴克"能搜到商户,但搜"拿铁"要搜不到;"买了杯拿铁"反过来。两样都写进去
(如"星巴克 拿铁一杯"),以后按商户名或按商品名都能命中先例。

**4. 用户确认后再调 `create_transaction`。**

## 修正一笔已有交易

用户说"上次那笔记错了""分类改一下"之类:先用 `search_transactions(keyword=...)`
或已知的交易 ID 找到那笔交易,再用 `update_transaction` 改。`update_transaction` 是
整字段替换语义,不是局部 patch——调用时把其余未变的字段(包括 `comment`)原样带上。

**这里有个不会报错的陷阱:`comment` 不是必填字段,漏传不会被拒绝,而是被静默清空成
空字符串——没有任何错误提示告诉你数据被清空了。** 所以调用 `update_transaction` 之前,
必须先用 `get_transaction` 把这笔交易当前的完整信息读出来,把 `comment` 原样复制进
这次调用,而不是凭记忆里的印象去拼参数。

**只改结构化字段(`source_id`/`category_id`/`amount`/`currency`/`time`),永远不要
顺手把 `comment` 也改写成解释性文字。** `comment` 只有在用户明确说"这段原文本身
记错了/写错字了"时才允许改动它自己;单纯是分类判断错了,不改 `comment`。

## 一笔跨多品类的消费:提议拆成多笔

一次超市结账、一个综合电商订单,常常一笔里混着分属不同分类的东西(食材 + 日用 +
零食)。这种消费**不要**自己挑一个笼统分类("购物")记成一笔——在第 2 步的对话预览里
提议按商品子类拆分,把拆分方案摆出来:每一笔的金额、分类、来源、`comment`。

- 触发条件:一笔消费的明细里出现明显分属不同分类的商品;或者是大额、多品类的单一
  商户消费,而你无法判断该归哪个分类。
- 每个子类的分类仍然逐笔走第 1 步的先例检索 + `list_categories`,**不要**在这里维护
  一张"什么商品归什么类"的固定规则表。
- 用户可以否决:用户说这笔不用拆,就按用户指定的单一分类记一笔。
- 用户确认拆分方案后,为每个子类分别调用一次 `create_transaction`。每一笔的
  `comment` 各自以商户原名开头、附上该笔对应的商品明细(如"沃尔玛 冷冻粽子×2"、
  "沃尔玛 洗洁精"),保证任取一笔都能被 `search_transactions` 单独搜到。

## 退款:冲回原支出的分类和来源

用户说某笔支出退款了:先用 `search_transactions(keyword=...)` 找到被退的那笔原始
支出,把退款记进**和原支出相同的**分类与来源——不要新建"退款"分类。金额方向按
`create_transaction` 现有的约定表示,并在第 2 步预览里标明这是对哪笔支出的冲回。

搜不到原始支出时,问用户这笔退款该冲回哪个分类和来源,不要自作主张建"退款"类目。

## 时间字段是无时区的本地日期时间字符串

`time` 是一个 `YYYY-MM-DD HH:MM:SS` 格式的字符串,不带任何时区标记——协议里从没有
时区概念,服务端原样存、原样还,不做任何时区解释或换算。它的含义就是用户记忆里的
墙上钟时刻:哪怕这笔账是用户在异地(比如境外旅行时)用当地时间记的,也原样写进去,
不要换算成用户惯常所在地的对应时刻,也不要为此追问用户当时身处哪个时区。

**把用户说的时间解析成 `time` 字符串之前,用 shell 的 `date` 命令算,不要心算、也不要
凭训练知识或对话里的印象猜"今天几号、星期几"。** 相对表达("今天""昨天""前天""上周五"
"3 天前")一律以当前日期为锚点算——Claude Code / claude.ai 的系统提示词本身就会把当前
日期注入进对话上下文,直接用它作锚点;没有看到这个上下文时,先自己跑一次 `date` 取
当前时刻,再据此推算。算出具体的年-月-日和时:分:秒后,直接格式化成
`YYYY-MM-DD HH:MM:SS` 写入,不需要再换算成任何其他单位。

解析完,在第 2 步的对话预览里把解析出来的日期、星期、时间摆出来,让用户看到你把这句
话解析成了"哪一刻"——解析错了,用户能在预览这一步就发现,而不是记进账本之后才发现
日期不对。

## 什么该写进 host 的记忆机制,什么不该

- **商户→分类映射、常用来源**:这是账本数据的投影,不是习惯。靠先例检索(第 1 步)
  从交易历史现算,永远不要写进你当前 host 的记忆机制(如 Claude Code 的
  MEMORY.md)——写了也会过时,账本数据本身就是最新答案。
- **用户本人的偏好**(记账时用什么语言、喜欢多细的分类粒度、几点提醒记账之类):
  这才是习惯层,可以写进 host 的记忆机制。

判据来自 tally 的分界原则:**习惯跟着它描述的对象走**——关于账本数据的,归先例检索;
关于用户本人的,才归 Agent 记忆。

## 不在这个 skill 范围内

批量导入、图片识别记账、定期交易调度——这些要么不在 tally 服务端范围内(交给 Agent
自己读图/解析),要么需要专门的 command 承接且尚未就绪。这个 skill 只管"记一笔/改
一笔"(含把一次消费拆成几笔)这种对话式的逐笔操作。
