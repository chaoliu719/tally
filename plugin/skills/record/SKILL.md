记一笔交易不是"调一次 create_transaction"这么简单。tally 把"账本数据的投影"(商户
惯用哪个分类、哪个来源、哪个预算)和"用户本人的偏好"(习惯层)分得很清楚——这个 skill 就是
在记录前后把这条边界落到具体动作上。

## 记录一笔新交易:标准流程

**1. 先例检索与预算选定。** 记录前先用 `search_transactions(ledger_id, keyword=<商户名/关键词>)`
搜这个账本里 `merchant` 或 `comment` 命中同一商户或同一关键词的历史交易。命中的交易里,
别人(也就是用户自己)之前用的 `source_id`/`category_id`/`budget_id` 就是先例——把它当默认值去用,
不要凭空猜,也不要每次都追问用户"这个算什么分类"。没搜到先例才需要问。

`keyword` 是大小写不敏感的子串匹配,**不支持通配符**——`%` 和 `_` 会被当成字面字符去
匹配,不是 SQL 里的模糊匹配符。不要为了"搜宽泛一点"往关键词里加这些符号,加了反而
可能因为原文里没有这个字面字符而搜不到。

**为每笔交易选定预算(`budget_id` 必填,收入与支出皆然)。** 预算与分类正交:分类回答
"钱花在什么上",预算回答"这笔钱在财务结构里算哪一类"(四个种子值:`固定` / `专项` / `突发` / `日常`)。
选预算按以下顺序,绝不直接由分类硬推:
- **先按这笔交易本身的性质判断**:周期性且刚性不可省的承诺(如房租、物业、年度车位费、固定套餐话费)归 `固定`;计划内为某件明确事情攒钱或一次性的大额项目(如旅行、装修、添置大件、专项聚餐)归 `专项`;计划外不得不花的意外支出(如突发看病、紧急维修、罚款)归 `突发`;其余日常流水(含利息收入等常规项)归 `日常`。性质能直接从商户、备注或金额看出来时,据此选定,不因分类而改判。
- **性质定不了时,依次查同商户先例、再查同分类先例**:如果第 1 步同商户的历史交易全部落在同一个预算,采用该预算;若同商户无先例,再看同分类历史交易是否稳定落在同一个预算。
- **仍定不了、历史出现多个不同预算、或本次金额明显偏离该商户/分类的历史区间时,直接向用户询问**该归哪个预算,不得自行猜测,也不得盲目套用默认值。

**四个预算在这一账本里的实际含义(判断时先对照这张表):**

- `固定`:每年、每月必须花的钱——物业费、水电气、话费网费、车位费、车险、社保医保、回老家路费等。
- `专项`:目前主要是两大类——电子产品(手机、平板及其配件的**大额**购置)与旅游(出游、国外购物)。它是"大额、计划内的整件事",不排除以后新增别的专项品类。
- `突发`:大额突发、应付突然的生病等意外支出。小额偶发不往这里放。
- `日常`:所有日常开销与小额偶然开销。**金额小就是日常**——哪怕它有明确用途(如为一次出游买的泳衣、一件有特定场合的衣服),也不因为"目的专一"就归专项;反过来,大额且属于固定或专项性质的钱,也不因为分类普通就留在日常。

**没搜到先例、且现有分类也没有合适的,才提议新建。** 没搜到先例时,先用
`list_categories(ledger_id)`(以及 `list_budgets(ledger_id)` 确认预算 id)看看账本里有没有语义匹配的已有分类——只有连这个都没有,
才需要新建。新建不要跳过预览直接建:把"准备新建一个叫 XX 的分类(挂在 YY 下面)"
作为预览的一部分,和金额/来源/预算等字段一起交给用户确认(见下一步)。用户确认后调用
`manage_category`(`operation="create"`)建好,拿到新分类的 `id` 后再据此记录;这是
非破坏性操作,不需要两步确认。如果用户不同意新建,追问该用哪个已有分类,不要自作
主张建。

**2. 对话预览,不直接写。** 检索完先例后,不要马上调 `create_transaction`。先在对话里
给用户一个结构化预览:金额、币种、来源、分类(如果分类是新建的,连同新建提议一起
展示)、**预算(并标明预算的选择依据:是来自交易性质判断,还是来自同商户/同分类的历史先例)**、发生时间、`merchant`(商户/收款方原名)、`comment`(你自己的备注)。商户名和
备注分两行展示,不要合并成一段。等用户确认或改完再写入。

这一步是纯对话层的软确认,和服务端的 `confirmation_token` 两步确认无关——那套机制只
用于破坏性/批量操作;`create_transaction` 本身是单步直写的工具,服务端不会替你二次拦。
预览是 skill 教的纪律,不是协议要求。

**3. 商户名与备注纪律。** 把两件事分开写:

- **`merchant` 是「这笔钱付给了谁 / 谁付的钱」的原名。** 银行账单上的商户名原样
  抄进去,不要改写成更顺口的名字、不要缩写、不要大小写归一;用户口述"星巴克 32 块"
  就写"星巴克"。现金、个人往来这类没有商户的交易,`merchant` 留空,不要编。
- **`comment` 是你自己想补充的话。** 用户说了"和同事下午茶""给妈妈买的"这类说明,
  才写进 `comment`;用户没额外说明就留空。不要把商户名重复塞进 `comment`,也不要把
  `comment` 写成"餐饮消费"这种归类结论。

这样以后 `search_transactions(keyword=...)` 既能用商户名搜到,也能用备注里的词搜到;
结构化字段(来源/分类)和文本字段(merchant/comment)各司其职,缺一层都会让先例检索变弱。

**4. 用户确认后再调 `create_transaction`。**

## 修正一笔已有交易

用户说"上次那笔记错了""分类改一下"之类:先用 `search_transactions(keyword=...)`
或已知的交易 ID 找到那笔交易,再用 `update_transaction` 改。`update_transaction` 是
整字段替换语义,不是局部 patch——调用时把其余未变的字段(包括 `budget_id`、`merchant` 和 `comment`)
原样带上,例如:
`update_transaction(id, ledger_id, type, source_id, category_id, budget_id, amount, currency, time, merchant, comment)`。

**这里有两个不同性质的陷阱:**
1. **`budget_id` 是必填字段,省略会直接被服务端拒绝(也不能传 `"0"`)。** 即使你只是想改一下分类或来源,用户完全没提预算,调用 `update_transaction` 时也必须原样带上这笔交易当前的 `budget_id`。
2. **`merchant` 和 `comment` 都不是必填字段,漏传不会被拒绝,而是被静默清空成空字符串——没有任何错误提示告诉你数据被清空了。**

所以调用 `update_transaction` 之前,必须先用 `get_transaction` 把这笔交易当前的完整信息读出来,
把 `budget_id`、`merchant` 和 `comment` 都原样复制进这次 `update_transaction(..., budget_id=..., merchant=..., comment=...)` 调用,而不是凭记忆里的印象去拼参数。

**只改结构化字段(`source_id`/`category_id`/`budget_id`/`amount`/`currency`/`time`),永远不要
顺手改 `merchant` 或 `comment`。** `merchant` 只有在银行/账单上的商户名本身记错了时
才允许修正;`comment` 只有在用户明确说"这段备注本身记错了/写错字了"时才允许改动。
单纯是分类或预算判断错了,两个文本字段都保持原样。

## 一笔跨多品类的消费:提议拆成多笔

一次超市结账、一个综合电商订单,常常一笔里混着分属不同分类的东西(食材 + 日用 +
零食)。这种消费**不要**自己挑一个笼统分类("购物")记成一笔——在第 2 步的对话预览里
提议按商品子类拆分,把拆分方案摆出来:每一笔的金额、分类、预算、来源、`merchant`、`comment`。

- 触发条件:一笔消费的明细里出现明显分属不同分类的商品;或者是大额、多品类的单一
  商户消费,而你无法判断该归哪个分类。
- 每个子类的分类和预算仍然逐笔走第 1 步的判断 + 先例检索 + `list_categories`,**不要**在这里维护
  一张"什么商品归什么类"的固定规则表。
- 用户可以否决:用户说这笔不用拆,就按用户指定的单一分类记一笔。
- 用户确认拆分方案后,为每个子类分别调用一次 `create_transaction`。每一笔共用同一个
  `merchant`(如"沃尔玛"),`comment` 写该笔对应的商品明细(如"冷冻粽子×2"、
  "洗洁精"),保证任取一笔都能按商户名或商品名被 `search_transactions` 单独搜到。

## 退款:冲回原支出的分类、来源和预算

用户说某笔支出退款了:先用 `search_transactions(keyword=...)` 找到被退的那笔原始
支出,把退款记进**和原支出相同的**分类、来源与预算(`category_id`、`source_id`、`budget_id`)——不要新建"退款"分类。金额方向按
`create_transaction` 现有的约定表示,并在第 2 步预览里标明这是对哪笔支出的冲回。

搜不到原始支出时,问用户这笔退款该冲回哪个分类、来源和预算,不要自作主张建"退款"类目。

## 时间字段是无时区的本地日期时间字符串

`time` 是一个 `YYYY-MM-DD HH:MM:SS` 格式的字符串,不带任何时区标记——协议里从没有
时区概念,服务端原样存、原样还,不做任何时区解释或换算。它的含义就是用户记忆里的
墙上钟时刻:哪怕这笔账是用户在异地(比如境外旅行时)用当地时间记的,也原样写进去,
不要换算成用户惯常所在地的对应时刻,也不要为此追问用户当时身处哪个时区。

**把用户说的时间解析成 `time` 字符串之前,用 shell 的 `date` 命令算,不要心算、也不要
凭训练知识或对话里的印象猜"今天几号、星期几"。** 相对表达("今天""昨天""前天""上周五"
"3 天前")一律以当前日期为锚点算——Claude Code / claude.ai 的系统提示词本身就会把当前
日期注入进对话上下文,直接用它作锚点;没有看到这个上下文时,先自己跑一次 `date` 取
当前时刻,再据此推算。算出具体的年-月-日和时:分:秒后,直接格式化成
`YYYY-MM-DD HH:MM:SS` 写入,不需要再换算成任何其他单位。

解析完,在第 2 步的对话预览里把解析出来的日期、星期、时间摆出来,让用户看到你把这句
话解析成了"哪一刻"——解析错了,用户能在预览这一步就发现,而不是记进账本之后才发现
日期不对。

## 什么该写进 host 的记忆机制,什么不该

- **商户→分类/来源/预算映射、常用来源**:这是账本数据的投影,不是习惯。靠先例检索(第 1 步)
  从交易历史现算,永远不要写进你当前 host 的记忆机制(如 Claude Code 的
  MEMORY.md)——写了也会过时,账本数据本身就是最新答案。
- **用户本人的偏好**(记账时用什么语言、喜欢多细的分类粒度、几点提醒记账之类):
  这才是习惯层,可以写进 host 的记忆机制。

判据来自 tally 的分界原则:**习惯跟着它描述的对象走**——关于账本数据的,归先例检索;
关于用户本人的,才归 Agent 记忆。

## 不在这个 skill 范围内

批量导入、图片识别记账、定期交易调度——这些要么不在 tally 服务端范围内(交给 Agent
自己读图/解析),要么需要专门的 command 承接且尚未就绪。这个 skill 只管"记一笔/改
一笔"(含把一次消费拆成几笔)这种对话式的逐笔操作。
