记账记了一段时间后,分类体系会跟不上——要么某个宽泛分类下悄悄长出了一个新爱好,
要么不同时间建的几个分类其实说的是同一件事。这个 skill 管怎么发现这两种情况、
怎么安全地拆分/合并,以及怎么在合适的时候提议定期复盘。**分类只能往粗了并、并不了
细,分细一点没关系**——所以默认偏细分是对的方向,拆分是在纠正"记录时想不到",
合并是在纠正"分得太细"。

## 发现信号

**拆分信号。** 检视某个较宽分类最近的交易时,如果其中一部分交易的 `comment`
明显反复指向同一个具体主题(比如"爱好"分类下最近连续出现好几笔和摄影器材相关的
记录),这就是该从中拆出一个更细子分类的信号。

**合并信号。** 检视账本全部分类(`list_categories`)时,如果发现两个在不同时间
创建、名称或实际记录内容明显指向同一含义的分类(比如"外卖"和"点外卖"),这就是
该合并的信号。

发现信号后不要自己直接动手——先把观察到的情况和具体建议告诉用户,等确认。

## 合并:先呈现影响范围,再执行

1. 用户同意把分类 A 合并进分类 B 之前,先用 `search_transactions(category_id=A)`
   数一下 A 下面有多少笔交易,挑几个例子给用户看看,**不要没展示过影响范围就直接
   开始改**。
2. **交易数量较大时,提前告知成本。** 没有批量更新工具——合并要对 A 下的每笔交易
   分别调用一次 `update_transaction`。如果数量不小(比如几十笔以上),先告诉用户
   大概要调用多少次、大致要花多久,让用户自己判断值不值得现在做。
3. 用户确认后,对分类 A 下的每一笔交易依次调用 `update_transaction`,把
   `category_id` 改成 B(其余字段——尤其是 `comment`——保持原样,做法同 `record`
   skill 里"修正交易"的纪律)。
4. 全部改完、A 不再被任何交易引用后,对 A 调用 `manage_category`
   (`operation="delete"`),走标准的 preview → apply 两步确认完成删除。

## 拆分:同样先呈现,再执行

1. 用户同意从某个分类拆出子分类后,先调用 `manage_category`(`operation="create"`),
   在原分类下建好新的子分类。
2. 把将要被移动过去的交易列表或数量展示给用户看一遍。
3. 确认后逐笔调用 `update_transaction`,把匹配的交易的 `category_id` 改成新分类。

## 提议周期性复盘:不要假设有哪个具体工具

判断适合建议用户定期(比如每周/每月)检查一下分类要不要拆分/合并时,**先看看
当前这次会话自己的工具箱/skill 列表里有没有宿主(harness)本身提供的定时/计划
任务能力**——有就用它设置提醒,没有就直接告诉用户这个环境做不到自动定时,建议
用户有空自己开口问。

这条 skill 不写死任何具体的定时工具名或调用方式。原因:定时能力是宿主环境给的,
不是 tally 或这份 plugin 自己实现的东西,不同环境是否有这个能力、叫什么名字都
可能不一样——但凡宿主真的支持定时,它自己就会像现在这次一样把对应的工具或 skill
放进模型自己的系统提示词里,不需要这份 skill 替它决定叫什么名字。

## 不在这个 skill 范围内

只管分类(category),不处理来源(source)——来源目前没有观察到类似的拆分/合并
需求。查数据、看趋势是 `analysis` skill 管的事,这里只管"分类体系本身该怎么调整"。
