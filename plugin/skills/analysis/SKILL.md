分析不是"调一次 `get_financial_summary` 把数字念出来"。这个 skill 管两件事:遇到
不同的分析类问题该拼哪个查询,以及查询结果里几个容易读错的语义细节。不做图表——
这块仍然按项目现有决定延后,这里只管文字/表格呈现。

## 时间换算:查询前、查询后各算一次,全程不许心算

`time` / `start_time` / `end_time` 都是不带时区语义的 Unix 秒。协议里没有时区概念,
服务端不校验、不提醒。**每次分析都必须做下面两步换算,一步都不能省。**

**第 0 步:确认时区。** 先跑 `date +"%Z %z"`(session 启动 hook 一般也给了锚点),
后面所有"本月/上月/今年/最近 N 天"和结果展示都按这个本地时区。

**查询前 —— 把时间窗口算成 epoch 秒再传:**
- 本月初:`date -v1d -v0H -v0M -v0S +%s`(macOS)
- 上月初 / 上月末:`date -v-1m -v1d -v0H -v0M -v0S +%s` 等
- "最近 30 天":`date -v-30d +%s`
- Linux 用 `date -d "..." +%s`

直接取命令输出塞进 `start_time`/`end_time`,不要凭感觉写数字。边界算错不会报错,
只会把跨月交易算进错的月份。

**查询后 —— 把返回的每个秒数字段反查成人类时间再写给用户:**
`date -r <ts> +"%Y-%m-%d %H:%M %Z"`(macOS)/ `date -d @<ts>`(Linux),换算到用户
本地时区。**绝对不要**把裸秒数丢给用户,也**绝对不要**自己脑补一个时区偏移去心算——
那正是时间显示全错的原因。

## 四种标准分析角度

**同类交易价格对比。** 用户想知道"这家店是不是又贵了"之类的问题:用
`search_transactions(ledger_id, keyword=<商户名/关键词>)` 把同商户/同关键词的历史
交易按时间取出来,直接对比 `amount` 走势作答。不需要 `get_financial_summary`——这是
单个商户级别的对比,汇总工具给不出这个粒度。

**月度环比。** 用户想知道"这个月比上个月花多了没":`get_financial_summary` 本身
没有"环比"能力,一次调用只给一个时间段的汇总。分两次调用——本月一次、上月一次,
各自传对应的 `start_time`/`end_time`——再把两次返回的 `income`/`expense`/`net` 和
按分类小计摆在一起对比。**月份边界的秒数自己算,服务端不认识"本月"这个词。**

**类别拆分对比。** 用户想知道"最近哪类花得多":一次 `get_financial_summary` 调用
返回的按分类拆分结果已经够用,不需要对每个分类单独查一次。

**多月/多年趋势。** 用户想看"连续几个月/这几年怎么变化的":按需要的粒度(月或年)
多次调用 `get_financial_summary`,把结果整理成一张走势说明或表格。**不画图**,纯
文字/表格呈现。

## 三条容易读错的解读规则

服务端对这几点不做任何校验或提醒,读错了不会报错,只会得出错误结论:

- **`net` 可能带负号,`income`/`expense` 恒非负。** 三个字段符号语义不一样,净支出
  时 `net` 是负数(比如收入 30、支出 50,`net` 是 `"-20.00"`),不要假设三者同号。
- **多币种分别返回,不做换算。** 账本里如果有多种币种的交易,`get_financial_summary`
  按币种分组分别给出汇总——不要把不同币种的金额直接相加或自己按汇率合并,展示时
  也分币种分别呈现。
- **分类/来源拆分只列出"有交易"的项。** 某个分类在统计范围内没有出现在拆分结果里,
  代表这段时间它没有收支,不是查询漏了或者出错了。

## 不在这个 skill 范围内

调整分类体系(拆分/合并分类)不是分析——那是 `optimize` skill 管的事,这里只管
"怎么问、怎么读",不涉及改动账本结构。

把某段时间或某商户的交易**原样列出来看**(不做合计/对比)是 `query` skill;记一笔/
改一笔是 `record`。
